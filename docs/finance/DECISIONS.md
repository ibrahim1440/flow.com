# Finance — design decisions (resolved 2026-09-26, implemented on the UAT candidate)

D2–D6 were decided by the owner on 2026-09-26 as **functional** decisions (not a statement
that pixel-level parity was verified). D4b and D7 were closed earlier and are retained.
Implemented on the local UAT branch `uat/finance-sales-20260926` (see UAT.md); Figma file
`CYWypOA4538FYoTDUdGyP5`, page "15 — Finance · Cash & Budget" updated to match.

Crops: `decisions/` holds the review-package crops (before); `decisions/uat/` holds the
application after implementation (`tests/finance/visual/uat-decisions-ui.mjs`) and the
updated Figma frames.

| ID | Decision (owner) | Implemented | Server rule / permission | Figma | Verified by |

| **D2** | Keep the extra review sections, collapsed by default; review status and primary action immediately visible. | Review panel: amount + review-status badge, notices, classification, splits and attachments visible; **Save and mark reviewed / Save without review / Confirm / Allocate by approved rules** in one visible action row. "Link to a document", "Review note" (before the actions) and "Allocated from this receipt", "History" (after) are native `<details>` sections, closed by default, each with a one-line summary (e.g. "لا يوجد", "اختيارية", "غير مخصص 2,250.00", "3 حدث"). The approved Sales collection for a receipt is suggested above the classification with a **Link collection** button. | unchanged; linking a collection needs `txn_enter` | FIN-02 review panel (329:261): status badge; four collapsed rows | UI check: status + primary action visible, 4 sections closed; workflow step 0 |
| **D3a** | Keep "New category" for authorized users; reuse the Settings form, validation and permissions. | There is no allocation-category form in Settings; the one form is the category dialog used for both create and edit. "New category" opens it (card's branch preselected). Same server validation (`parseCategoryBody`, `checkCategoryShape`) and the same duty as edits (`budget_prepare`); hidden without it. | `POST /api/finance/categories` → `budget_prepare` (403 otherwise) | FIN-03: "+ فئة جديدة" in the categories header | HTTP: viewer 403; UI: viewer sees no button |
| **D3b** | Concise explanation that allocated cash is not necessarily distributable profit, near profit-related categories or in contextual help. | The footnote under every table is removed. The explanation appears under the name of a profit-like category (name/code: profit, dividend, distribution, owner/partner share or draw, أرباح/ربح/توزيع/حصة المالك/مسحوبات) and in the category form while such a name is typed. | — | FIN-03: example row "حصة أرباح المالك" with the explanation | unit (11 name cases); UI: one hint on the fixture's profit-like category, none elsewhere |
| **D4a** | Keep the line owner. Incomplete-data warnings only when supported by actual completeness indicators; a verified zero distinguishable from missing data. | Owner kept. The unconditional "data may be incomplete" is gone. Each row now carries its own indicators: lines awaiting review or pending **in the row's direction** that are unclassified or classified to **that category**, and accounts not reconciled through the report date. Zero actual + no indicator → "صفر مؤكد" (verified zero); otherwise "لم يُتحقق بعد: …" naming what is outstanding. | `budgetReport` → `rows[].completeness` (`lib/finance/completeness.ts`) | FIN-04: owners under three lines; the two zero rows show their indicators | unit (5); DB (per-row: direction, category, reconciliation); UI |
| **D5** | Keep counterparty, Show all, Export and Cancel; existing permissions; cancellation reason required; auditable reversal where financial effects exist. | Counterparty, Show all, Export kept. Cancel opens a dialog that first shows the effects (remaining that stops counting; paid that stays; payment requests that will be released) and requires a reason (≥ 5 characters). Payment requests holding money are released with their own audited release (`allocate` duty required, else refused); paid amounts stay recorded and matched (cash that left is not reversed); the cancellation's audit entry records paid retained, remainder cancelled and requests released. | `budget_prepare` (unchanged) + `allocate` when requests must be released | FIN-05: cancel column, counterparties, Show all, Export; new FIN-07e cancel dialog | DB (3 tests); HTTP (short reason 400, viewer 403); UI (confirm disabled without a reason) |
| **D6** | Keep the account fields and branch-access configuration; suggested categories optional; access changes only by authorized administrators, audited. | Account fields kept. Branch access grant/revoke requires finance `settings_manage` + `all_branches` **and** the ERP's employee-edit authority (the authority that edits permissions elsewhere); nobody changes their own access; a repeat grant changes nothing. Each change is audited with before/after, employee name, branch code and the actor. "Add suggested (optional)"; Finance works with hand-made categories only. | `setBranchAccess`: 403 otherwise; own id refused | FIN-06: second row of account fields, "إضافة المقترحة (اختياري)", inline new-category form, administrator-only note; new FIN-06b administrator view | DB (access rules + audit; finance without suggestions); HTTP (preparer 403, self 403); UI |

## 4. Harness (ready; exercised only with a stub)

Run:

```
SDK_ARCHIVE=<zip> SDK_SHA256=<sha-256> SDK_SOURCE_URL=<zatca.gov.sa URL> \
  bash scripts/accounting/zatca-sdk-validate.sh docs/accounting/evidence/zatca/matrix-19f3639 <outDir>
```

**Checks before anything runs:**
- the archive's SHA-256 matches `SDK_SHA256`, and `SDK_SOURCE_URL` is a zatca.gov.sa URL;
- Java is 11–14;
- each command is run only if its exact syntax appears in **the archive's own readme**:
  `fatoora -validate -invoice <file>` and `fatoora -generateHash -invoice <file>`. These are the
  forms documented in the copies seen; a command missing from the official readme makes the harness
  stop.

**Installation:** the harness runs `install.sh` as the readme describes, inside an isolated `HOME`
under `<outDir>`. Nothing outside `<outDir>` changes.

**Outputs:**
- `provenance.txt`: archive, URL, both hashes, jar name and hash, the readme's Java lines, the Java
  version used;
- per document, the raw `validate.out` and `generateHash.out` with their exit codes;
- `SUMMARY.md`, which quotes only lines the SDK printed, and states whether the SDK's hash equals
  ours.

**Certificates:** the SDK's shipped test certificate and key are left as shipped, as its readme
documents. None is created or edited, and tag 9 is never fabricated.

**How it was tested:** only with an archive built here, whose `fatoora` is a stub printing a fixed
line. That confirmed the guards (wrong URL, wrong hash, undocumented command → refused) and the
plumbing. **It is not an SDK run.**

## 5. What the SDK run is expected to show (developer review; not validator findings)

Read from our own XML. Each item is a question for the SDK, not a confirmed defect, and none was
"fixed" blind:

1. **Signature** — the simplified documents carry a LOCAL test signature in a non-standard
   extension, **not XAdES**: no `ds:SignedInfo` and no `xades:SignedProperties`; it signs the hash
   bytes rather than a canonical `SignedInfo`. Signature, certificate and QR-stamp checks are
   expected to fail until XAdES is implemented with the SDK's documented test certificate.
2. **Invoice hash** — computed over our deterministic serialisation with signature and QR parts
   removed by string operations, not over the canonicalised (C14N 1.1) XML after the standard's
   transforms. `fatoora -generateHash` will show whether it matches.
3. **Supply date** — standard invoices carry no `cac:Delivery/cbc:ActualDeliveryDate` unless the
   sales document has a supply date.
4. **Line discounts** — expressed only as `MultiplierFactorNumeric` inside `cac:Price`, without an
   allowance amount or base amount.
5. **Standard invoices** — they are not signed by us and carry a QR with tags 1–5 only. Whether
   the taxpayer must stamp them before clearance is to be confirmed with the SDK and the clearance
   API.
6. **Exemption codes** — synthetic; must match the official code list.
7. **QR tags 6–8** — follow the official documents as cited (32-byte hash, P1363, 64-byte key),
   which conflicts with the third-party SDK samples. The SDK settles it; see
   `ZATCA_REQUIREMENTS.md` §3.
8. **Curve** — secp256k1. The certificate profile is to be confirmed from the official SDK's
   configuration and the onboarding documents.

## 6. Effect of future encoding changes on issued documents

E-invoice rows are immutable (database trigger): their XML, hash, QR and signature never change.
- A change to hashing or canonicalisation, XAdES or the QR layout applies only to documents
  generated after it.
- The chain continues from each document's *stored* hash, so earlier documents keep their place.
- Re-running the local rules on a document stored in an older layout reports `LOCAL-QR-HASH` /
  `LOCAL-QR-STAMP` failures, which is expected and recorded in the rule details.
- Nothing has been issued outside test databases: production has no e-invoices.
- Before any release, documents generated by test runs must not be migrated.
